# Claude Code 사용 패턴 & 작업 규칙

> 이 문서는 2026-06-08 ~ 07-14 사이 23개 세션(실제 프롬프트 382건)을 분석해 정리한 것입니다.
> 새 세션을 시작하거나 다른 사람이 작업을 이어받을 때, 아래 리듬과 규칙을 따르면 기존 방식과 일관됩니다.

---

## 1. 개요 — 작업 환경

- **프로젝트**: Next.js 14 기반 사내 디자인 갤러리(Design5). 카테고리별 게시물 갤러리(Penta Design, ICON/ICON+, HW, eDM, Brochure, INSIGHTS 등) + 관리자 기능.
- **환경 3단계**
  - **로컬** — 코드 작성/구현. 단, DB·Storage가 없어 UI 일부만 확인 가능(터널 필요).
  - **design6 (개발망)** — `https://design6.pentasecurity.com`. **실제 검증은 여기서** 함. DB·MinIO Storage가 사내 개발서버에만 존재하고 외부 접속 불가.
  - **design5 (운영망)** — `https://design5.pentasecurity.com`. 개발망 검증 완료 후 반영. (컨테이너/박스 이름이 `design5`로 되어 있어 개발망과 혼동 주의.)
- **핵심 제약**: DB/Storage가 외부에서 안 보이므로 **로컬 자동 테스트로는 검증이 안 되고, 개발망에서 사람이 직접 테스트**해야 함.

## 2. 작업 리듬 — Phase 단위 점진 구현

큰 기능은 항상 **단계(Phase 0~7 / P0~P6)로 쪼개고, 한 단계씩 승인하며 진행**한다.

- 흐름: `구현 계획 수립 → 단계별로 "네, P1 진행해 주세요" → 검증 → 다음 단계`
- 한 번에 전체를 구현하지 않는다. 각 단계가 끝나면 개발망 검증을 거친 뒤 다음 단계로.
- 애매한 항목은 뒤 단계로 이관한다. (예: "미정 사항은 phase 6 항목으로 이관")

## 3. 세션 연속성 — Handoff 문서 & 사용량 관리

### Handoff 문서
- 기능마다 `docs/*_handoff.md` 문서를 만든다. (예: `REFACTORING_HANDOFF.md`, `ICON_PLUS_handoff.md`, `PENTA_DESIGN_MEDIA_handoff.md`)
- 새 세션은 **"@docs/XXX_handoff.md 기준으로 P3부터 진행해주세요"** 처럼 문서를 기준으로 이어간다.
- 문서에는 진행 상태·잔여 작업·검증 체크리스트·다음 단계를 기록한다.

### 세션 사용량 관리
- 세션 사용량(%)을 직접 확인한다. ("현재 88% 사용 중입니다. P3 구현이 가능할까요? 답변만 부탁해요")
- **리밋에 가까워지면 다음 순서로 마무리**: ① handoff 문서 업데이트 → ② 커밋/푸시 → ③ 다음 세션에서 이어감.

## 4. 개발망 검증 루프 (작업의 핵심 축)

가장 자주 반복되는 사이클:

```
Claude 구현
   ↓
"사내망 테스트를 위해서 커밋 푸시해주세요"   ← 시그니처 문구
   ↓
사용자가 개발망(design6)에서 직접 테스트 (UI/업로드/기능)
   ↓
결과 피드백 (로그·스크린샷 첨부)
   ↓
수정 → 다시 커밋/푸시 → 재검증  (반복)
```

- **왜 로컬이 아니라 개발망인가**: DB·Storage가 개발서버에만 있어서 로컬에서는 이미지 업로드/조회 등 핵심 기능이 재현되지 않음.
- 커밋/푸시는 검증을 위한 **배포 트리거** 역할. 기능 완성이 아니라 "개발망에서 확인해 보기 위해" 푸시하는 경우가 많다.

## 5. 신중한 진행 규칙

### "먼저 답변, 실행은 나중에"
- 코드를 바꾸기 전에 **"답변만 / 설명만 / 확인만 / 검토만 부탁해요"** 로 분석·설명을 먼저 요청한다.
- 즉, **분석 → 사용자 확인 → 그 다음 구현**. 곧바로 코드 수정에 들어가지 않는 것을 선호.

### 방안 선택형 진행
- 여러 방안을 제시받고 고른다. ("방법 1으로 진행", "A안으로", "권장 방안으로", "1+2+3 조합으로")
- 권장안이 있으면 대체로 권장안을 따르되, 이유를 먼저 듣고 결정.

### 데이터 안전
- 마이그레이션/스키마 변경 시 **DB 데이터 보존을 명시적으로 요구**한다. ("마이그레이션 시 DB 데이터 삭제 안되게 주의해주세요")

## 6. 배포 · 인프라 규칙

- **배포 방식**: 로컬에서 `git push` → 서버에서 `git pull`. (FileZilla 등으로 파일 일일이 복사하지 않음)
- **푸시 브랜치**: 항상 `2026-06-17-tiper` 브랜치로 푸시. (로컬 브랜치명과 다를 수 있으니 확인)
- **신규 컬럼/스키마 배포 시**: 개발망에 `prisma migrate deploy`를 먼저/함께 적용. (안 하면 해당 테이블 쿼리가 전부 실패)
- **함께 다뤄온 인프라 이슈**(로그를 붙여넣고 같이 디버깅):
  - 환경변수 — `S3_PUBLIC_BASE_URL`, `S3_PUBLIC_ENDPOINT`, `NEXT_PUBLIC_*` 등 (design5/design6 혼용 주의)
  - nginx 리버스 프록시 — PUT 허용, `Host` 헤더 보존
  - MinIO / presigned URL — 이메일(eDM) 이미지 경로가 presign 쿼리스트링 때문에 깨지는 문제 등

## 7. 커뮤니케이션 규약

- **언어**: 한국어 존댓말.
- **에러 보고**: 콘솔/터미널/빌드 로그를 **통째로** 붙여넣는다.
- **UI 피드백**: 스크린샷(첨부 이미지)으로 "이 부분을 이렇게" 식으로 전달.
- **파일 경로**: **프로젝트 루트 기준**으로 알려줄 것. ("이후부터는 루트부터 경로를 알려주세요")
- **변경 파일 목록**: 사내망 반영을 위해 "이번에 수정/추가된 소스 파일을 알려주세요" 를 자주 요청.
- **마무리**: 단계가 끝나면 "고생했어요 / 고마워요" 로 정리하고 다음 세션 예고.

### 작업 성격
- 갤러리 카테고리 페이지의 **UI 세부 조정**이 큰 비중: 여백, 색상·그라데이션, 반응형(모바일 너비), 슬라이드/애니메이션, 배지, 다이얼로그.
- **일관성**을 중시. ("다른 메뉴 페이지에도 동일하게 적용해주세요")

## 9. 더 나은 활용 방법 (개선 제안)

현재 워크플로는 신중하고 안정적이지만, **"개발망에 사람이 직접 배포·검증"에 크게 의존**해서 한 바퀴가 느립니다. 아래는 실제 과거 기록에서 병목이었던 지점을 겨냥한 개선안이며, **효과가 큰 순서**로 정리했습니다.

### ⭐ A. 반복 규칙을 `CLAUDE.md`로 자동화 — (효과 큼 / 노력 작음)
- 지금은 매 세션 같은 규칙을 말로 반복하고, 이 문서에 적혀만 있어 **Claude가 자동으로 따르지 않습니다.** (프로젝트에 `CLAUDE.md`가 아직 없음)
- 프로젝트 루트에 `CLAUDE.md`를 만들어 §5·§6·§7의 **하드 규칙**을 넣으면 모든 세션에서 자동 적용됩니다:
  - 푸시 브랜치는 항상 `2026-06-17-tiper`
  - 신규 컬럼/스키마 배포 시 개발망에 `prisma migrate deploy` 선적용
  - 마이그레이션 시 DB 데이터 보존
  - 파일 경로는 프로젝트 루트 기준으로 안내
  - design5(운영)/design6(개발) 구분, 컨테이너명 혼동 주의
- 이 문서는 "설명서", `CLAUDE.md`는 "자동 적용되는 규칙"으로 역할을 나눕니다.

### ⭐ B. 푸시 전 로컬 preflight — (효과 큼 / 노력 작음)
- 과거 기록상 **개발망 rebuild 후에야 발견한 에러 중 상당수가 로컬에서 즉시 잡히는 컴파일·경로 에러**였습니다. (예: `Module not found: @/components/.../MainLayout`) → 느린 `push → pull → docker build(50초+) → 수동 테스트` 사이클을 통째로 낭비.
- 이미 스크립트가 다 있으니, **"커밋 푸시" 전에 로컬에서** 아래를 먼저 돌리면 왕복이 크게 줄어듭니다:
  ```bash
  npm run typecheck && npm run lint && npm run build
  ```
- "커밋 푸시해주세요"라고 할 때 **Claude가 preflight를 먼저 통과시킨 뒤 푸시**하도록 규칙화하면 좋습니다. (CLAUDE.md에 명시)

### C. 반복 의식을 슬래시 명령으로 자동화 — (효과 중 / 노력 작음)
`.claude/commands/`에 커스텀 명령을 만들면 매번 풀어 설명할 필요가 없습니다:
- `/preflight` — typecheck + lint + build 실행
- `/ship` — preflight 통과 시 커밋 + `2026-06-17-tiper`로 푸시
- `/handoff` — 해당 handoff 문서 갱신 + 커밋 + 푸시를 한 번에
- (선택) Stop 훅으로 응답 종료 시 자동 typecheck 등도 가능.

### D. 로컬 재현 스택으로 "자가 검증" — (효과 큼 / 노력 중, 중기 과제)
- 현재 검증이 전부 사람+개발망에 묶여 있어 느립니다. 로컬에 **postgres + MinIO를 띄우는 dev용 docker-compose + `npm run db:seed`**를 구성하면, Claude가 로컬에서 앱을 실행해 업로드/조회 같은 기능을 **스스로 확인한 뒤** 넘길 수 있습니다. 개발망은 최종 확인용으로만.
- 주의: CI/자동 테스트는 DB 독립 원칙을 유지하고, 이건 **로컬 수동·자가 검증 전용 일회용 스택**으로 분리합니다.

### E. design5 외부 공개 전 보안 점검 — (공개 예정이므로 중요)
- design5가 곧 외부 공개될 예정이므로, 공개 전에 `/security-review`로 **인증·관리자 전용 라우트 권한, 업로드 검증, presigned URL, RLS**를 점검하세요. 이미 관련 문서(`POSTGRES_RLS_INTERNAL.md`, `SUPABASE_SECURITY_SETUP.md`)가 있으니 함께 확인.

### F. UI 작업 고도화 — (님 작업의 큰 비중)
- **Figma MCP 커넥터**: 디자인 → 코드 변환, 디자인 토큰/컴포넌트 동기화로 여백·색상·반응형 반복 조정을 줄입니다.
- **여러 페이지 일괄 적용**: "다른 메뉴에도 동일하게"가 잦으니(일관성 중시), 서브에이전트/병렬 작업으로 여러 카테고리 페이지를 한 번에 수정할 수 있습니다.
- **스크린샷 자가 검증**: 로컬 스택(D)이 갖춰지면 Claude가 브라우저로 화면을 캡처해 기대 디자인과 대조할 수 있습니다.

### G. Plan mode·서브에이전트 활용 — (님 스타일과 잘 맞음)
- **Plan mode**(Shift+Tab): 큰 기능 착수 전 계획을 먼저 세우고 승인받는 모드. 님의 **"답변만/설명만 먼저"** 패턴과 정확히 같은데, 더 구조화되어 있습니다.
- **Explore/Plan 서브에이전트**: 리팩토링·영향 범위 조사처럼 여러 파일을 훑어야 할 때 위임하면 빠릅니다.

> **가장 먼저 권하는 3가지**: ① `CLAUDE.md` 만들기(A) → ② 푸시 전 로컬 preflight 습관화(B) → ③ design5 공개 전 보안 리뷰(E). 이 셋만으로도 개발망 왕복과 리스크가 눈에 띄게 줄어듭니다.
