# 로컬 작업 및 개발망 작업 시 주의 사항

## 로컬 작업 주의 사항

1. 로컬에서는 **읽기 전용 검증** 까지만하고 **게시물 저장·이미지 업로드 같은 **쓰기 동작** 테스트는 반드시 **design6.pentasecurity.com 에서 해야 함

- 코드 작성 및 타입 체크, `npm run build`는 로컬에서 하되, **게시물 저장·이미지 업로드 같은 쓰기 동작 테스트는 design6에서** 해야함 (로컬 쓰기는 운영 DB를 오염시킴)

2. 소스 수정 및 업로드

- 소스코드는 로컬에서 수정한 후 **타입체크** 와 **빌드성공** 만 테스트한다.
- 수정 된 코드는 반드시 **2026-06-17-tiper** 브런치로 업로드 한다.
- **⚠️ push 대상 브랜치는 항상 `origin/2026-06-17-tiper` 이다.** 로컬 작업 브랜치명(예: `refactor/phase2-api-layer`)이 이와 다를 수 있으므로, 로컬 브랜치를 그대로 push하지 말고 반드시 원격 `2026-06-17-tiper`로 올린다.
    - 로컬 브랜치가 `origin/2026-06-17-tiper`를 fast-forward 하는 상태인지 먼저 확인:
        ```sh
        git fetch origin 2026-06-17-tiper
        git rev-list --left-right --count origin/2026-06-17-tiper...HEAD   # 왼쪽(origin 전용)이 0이어야 안전
        ```
    - push (로컬 브랜치명과 무관하게 원격 대상 명시):
        ```sh
        git push origin HEAD:2026-06-17-tiper
        ```
    - 개발망 서버는 이 `2026-06-17-tiper`를 `git pull` 하므로, push하지 않은 변경은 서버 리빌드에 반영되지 않는다.

## 개발망 빌드 방법

1. 사내 개발망 접속

```js
ssh design@192.168.1.43 -p 6022      // 비번입력
```

2. 소스 코드 받기

```js
cd /data/webapps/design5/   // 프로젝트 루트로 이동

// git pull/push 주소 확인하기, `2026-06-17-tiper`를 체크아웃 중인지 먼저 확인
git branch --show-current   // 2026-06-17-tiper 여야 함
// git remote set-url origin "새로운주소"  // 만약 리모트 주소가 잘못되었다면 변경함

git pull                    //  git pull --ff-only 옵션 사용하면 더 안전함
git log --oneline -2        //  pull 명령으로 받은 소스의 최근 커밋 확인

// 이제 빌드 위치로 이동
cd /data/webapps/design5/deploy/rocky

docker ps  // 도커의 DB/MinIO 가 실행 중인지 확인
// docker compose -f docker-compose.yml --env-file .env up -d   // 안 떠 있으면 먼저 띄운다. - 일반적으로 떠 있음

//  아래 명렁어 입력해서 리빌드한다. (리빌드 명령어)
//  --no-deps : app 컨테이너만 다시 만든다 (postgres·minio는 건드리지 않음)
docker compose -f docker-compose.yml -f docker-compose.app.yml --env-file .env.app up -d --build --no-deps app

// 리빌드 후 앱이 실제 떴는지 확인할 수 있음 ,  Ready in 98ms 메시지 보여야함
docker logs design5-app --tail 30

// ⚠️ 리빌드 후 반드시 nginx 재시작 (안 하면 502 Bad Gateway) — 실행 경로 무관
docker restart design5-nginx
docker ps   // design5-nginx 의 STATUS 가 "Up N seconds" 인지 확인
```

> **왜 필요한가 (2026-09-30 개발망 502 사례)**
> - nginx 설정(`nginx/app-http.conf`)은 `proxy_pass http://app:3000;`, `http://minio:9000` 처럼 컨테이너 이름으로 연결한다.
> - nginx는 이 이름의 IP를 **시작할 때 한 번만 조회**해서 계속 쓴다.
> - 리빌드로 app(또는 postgres·minio) 컨테이너가 새로 만들어지면 IP가 바뀔 수 있다. 그러면 nginx가 옛 IP로 연결하다 **502 Bad Gateway**가 난다.
> - 그래서 리빌드 후 nginx를 재시작해 새 IP를 다시 조회하게 한다. 재시작은 몇 초만 끊기고 데이터에는 영향이 없다.
> - `--no-deps` 없이 리빌드하면 compose가 의존 서비스(postgres·minio)까지 다시 만들 수 있다. 이번 사례에서도 세 컨테이너가 모두 새로 만들어졌다.
>   - 이때 `.env.app`에 `DATA_ROOT`가 없으면 데이터 폴더가 `${DATA_ROOT}/postgres` → `/postgres`처럼 **엉뚱한 빈 폴더로 연결될 수 있다**. 기존 데이터가 지워지지는 않지만 사이트가 비어 보인다.
>   - 그래서 app만 다시 만든다. 운영망(design5)에서도 같은 절차를 따른다.
> - postgres·minio 자체를 다시 띄워야 할 때는 위의 `docker compose -f docker-compose.yml --env-file .env up -d`(데이터 평면, `.env` 사용)로 따로 실행한다.

## 데이터/마이그레이션 스크립트 실행 (백필 등)

- ⚠️ **개발망 호스트에는 node/npm이 없다** (`npm: command not found`). 앱 컨테이너도 `output: 'standalone'` 이미지라 `tsx`·`scripts/`·전체 `node_modules`가 없어 컨테이너 안에서도 `npm run db:*` 실행 불가.
- 따라서 `db:seed`, `db:migrate-*`, `db:backfill-*` 같은 **tsx+Prisma 스크립트는 "로컬에서 DB 터널로" 실행**한다:
  ```sh
  # 1) 로컬에서 개발망 DB/Storage 터널 연결
  ssh -N -L 15432:127.0.0.1:5432 -L 19000:127.0.0.1:9000 -p 6022 design@192.168.1.43

  # 2) 로컬 .env 의 DATABASE_URL 이 127.0.0.1:15432 (=개발망 DB) 를 가리키는지 확인 후, 로컬에서 실행
  npm run db:backfill-icon-groups:dry   # 예: 미리보기(쓰기 없음)
  npm run db:backfill-icon-groups       # 실제 반영
  ```
- 데이터 작업은 `git push`/리빌드로 옮겨지지 않는다(코드만 이동). 개발망(design6) → 검증 → 운영망(design5) 각각 실행한다.
